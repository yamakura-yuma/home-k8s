# Claude Code のテレメトリの使い方 (場面別)

Grafana のダッシュボードを、困りごとから引くための手引き。場面ごとに
「どのダッシュボードのどのパネルを見るか → 何が分かるか → ハーネスのどこを直すか」を書く。
同じ内容を短くしたものが、Grafana の「Claude Code はじめに」(`/d/claude-code-start`) にある。
観測スタックの構成は [claude-code-traces.md](claude-code-traces.md)、各ダッシュボードの
パネルの意味は [claude-code-usage.md](claude-code-usage.md) と
[claude-code-improve.md](claude-code-improve.md) にまとめている。OTel の設定 (環境変数) ごとに何が届くかは
[claude-code-settings.md](claude-code-settings.md) と、Grafana のフォルダ「Claude Code 設定項目別」(`/d/cc-settings`)。

## 用語

| 語 | 意味 | このスタックでの置き場所 |
|---|---|---|
| メトリクス | 一定間隔で送られる数値の累計。コストやトークン数など | Prometheus (`claude_code_*`) |
| ラベル | メトリクスの内訳を分ける名前と値の組 (`model="claude-sonnet-5-5"` など)。ログの属性も Grafana ではラベルと呼ぶ | 各データの列 |
| ログ (イベント) | 出来事 1 回につき 1 行の記録。依頼文、API 呼び出し、ツール実行などの種類 (`event_name`) と属性を持つ | Loki (`service_name="claude-code"`) |
| トレース | 1 つの依頼の処理全体を、入れ子の区間の木として記録したもの | Tempo |
| スパン | トレースを構成する 1 区間。開始時刻・所要時間・属性を持つ (LLM 呼び出し 1 回、ツール実行 1 回など) | Tempo |

## ダッシュボード

| 名前 | 使う場面 |
|---|---|
| Claude Code はじめに (`/d/claude-code-start`) | 入口。この文書の短縮版と各ダッシュボードへのリンク |
| Claude Code raw (`/d/claude-code-raw`) | 何が届いているかを信号ごとにそのまま見る。集計を作る前、属性名を調べるとき |
| Claude Code usage (`/d/claude-code-usage`) | コスト・トークン・ワーカー別の量 |
| Claude Code traces (`/d/claude-code-traces`) | 所要時間、ツール、hook、サブエージェントの内訳 |
| Claude Code improve (`/d/claude-code-improve`) | ハーネスを直す箇所を決める。依頼ごとのコスト、失敗したコマンド、skill の使われ方 |
| Claude Code 設定項目別 (`/d/cc-settings` から各設定へ) | OTel の設定 1 つごとに、その設定で届くようになった属性・ラベルを全部見る。設定を変える前後に使う |
| Orca orchestration (`/d/orca-orchestration`) | coordinator が Orca でワーカーをどう回したか。追加指示・question・worker_done までの時間などの手戻りと、ワーカー別のコストの突き合わせ、話題別・役割別のコスト。データの出どころは [orca-orchestration.md](orca-orchestration.md) |

どのダッシュボードも右上の期間で集計範囲が変わる。上部の「Claude Code」リンクで互いに
行き来でき、期間は引き継がれる。

## 場面

### 1. 今日いくら使ったか、どのワーカー・モデルが高いか

- 見る: usage の「今日のコスト」「モデル別コスト」、「3. ワーカー別」の「ワーカーごとの集計」。
- 分かること: 期間中のコストの合計と、モデル別・ワーカー (Orca の worktree) 別の内訳。
  ワーカー名が「(Orca の外)」の行は、Orca を通さずに起動したセッション。
- 次にすること: 高いワーカーが分かったら、場面 2 でその中の高い依頼を探す。
  モデル別で Opus が大半なら、場面 6 の手順で Sonnet に回せる作業がないかを検討する。

### 2. ある依頼がなぜ遅かったか・高かったか

- 見る: improve の「コストの高い依頼 (上位 20)」。特定の依頼を探すときは、上部の「依頼文」欄に
  依頼文の一部を入れて「依頼文の検索結果 (新しい順)」を見る。
- 分かること: 依頼ごとのコスト、API 呼び出し回数、ツール呼び出し回数、所要時間。
  依頼文をクリックして「トレースを開く」を選ぶと、ウォーターフォール (スパンの木と所要時間) が開く。
  長いスパンが `claude_code.llm_request` なら LLM の応答待ち、`claude_code.tool` ならツールの実行、
  `claude_code.tool.blocked_on_user` なら許可待ちが時間を使っている。
- 次にすること: LLM 呼び出しの回数が多いなら、依頼 (spec) に完了条件や読むべきファイルを書き足して
  探索を減らす。許可待ちが長いなら、よく使うコマンドを settings の許可リストに入れる。
  ツールの実行が長いなら、そのコマンド自体を速くするか、結果を絞る (出力が大きいと次の LLM 呼び出しも重くなる)。

### 3. 同じコマンドの失敗が繰り返されている

- 見る: improve の「失敗したコマンド (回数の多い順)」と「直近の失敗 (行を開くとトレースへ)」。
- 分かること: 失敗したコマンドと、その回数・エラーの中身。同じコマンドが何度も並ぶなら、
  エージェントが正しい使い方を知らずに試行錯誤している。
- 次にすること: 正しい手順 (引数、前提条件、代わりのコマンド) を skill に書き足す。
  リポジトリ固有の手順なら、そのリポジトリの rule か README に書く。1 週間後に同じパネルで回数が減ったかを見る。

### 4. 入れた skill が使われていない

- 見る: improve の「skill ごとの呼び出し回数」。raw の「2. ログ / イベント」でイベント種別
  `skill_activated` を選ぶと、いつどの skill が起動したかの生の行が見られる。
- 分かること: 期間中に起動した skill とその回数。入れたはずの skill が表に無ければ、一度も起動していない。
- 次にすること: skill の description (起動するかどうかの判断に使われる文) を、実際の依頼で使われる
  言い回しに合わせて書き直す。数週間使われていないなら外す。常時読み込まれる一覧が短くなり、
  場面 5 のキャッシュにも影響する。

### 5. キャッシュが効いていない

- 見る: improve の「キャッシュ読み出し割合」「ワーカー別のキャッシュ読み出し割合」
  「キャッシュ読み出し割合の推移」。モデル別に見るなら traces の「モデル別のキャッシュ読み出し割合」。
- 分かること: 入力トークンのうち、キャッシュから読んだ割合。割合が低いワーカーは、
  毎回プロンプトの先頭が変わっているか、会話が短く切れている。
- 次にすること: 常時読み込まれる rule や CLAUDE.md に、実行のたびに変わる内容 (日付、状態) を
  入れていないかを確かめる。常時読み込みの rule を小さくし、場面にだけ要る手順は skill に移す。
  途中でモデルを切り替えるとキャッシュは作り直しになるので、切り替えの頻度も確かめる。

### 6. Sonnet に回した作業が手戻りしていないか (モデル選択の検証)

- 見る: usage の「ワーカー × モデルのトークン」でどのワーカーがどのモデルで動いたかを確かめ、
  improve の「ワーカーごとの依頼数と 1 依頼あたりの往復」で、そのワーカーの依頼数・往復回数・
  ツールの失敗数を比べる。
- 分かること: 同じ種類の作業で、Sonnet のワーカーだけ 1 依頼あたりの往復や失敗が多いなら、
  やり直しが起きている可能性がある。依頼数が多い (同じワーカーに何度も指示を出し直している) のも手戻りの兆候。
- 次にすること: 手戻りが多い種類の作業は Opus に戻すか、spec に手順と完了条件を細かく書いて
  Sonnet のまま続ける。どちらにしたかを記録し、場面 8 の手順で前後を比べる。
  1 依頼あたりのコストは Sonnet が安くても、往復が増えると合計では逆転することがある。

### 7. サブエージェントやリサーチが何をどの順で調べたか

- 見る: traces の「サブエージェントを含む依頼」から Trace ID をクリックする。
  個々のツール呼び出しの属性を見たいときは、raw の「3. トレース」で
  スパン名 `claude_code.tool` を選び、「最近のトレース」の行を開く。
- 分かること: ウォーターフォールで、サブエージェント (tool_name が Agent / Task のスパン) の下に
  どのツールがどの順に並び、それぞれ何秒かかったか。スパンを開くと、実行したコマンド
  (`full_command`) や読んだファイル (`file_path`) が属性として見える。
- 次にすること: 同じファイルを何度も読んでいる、関係のないディレクトリを探しているなら、
  サブエージェントへの指示に調べる範囲と止める条件を書き足す。コードの場所を探す検索が多いなら、
  コードの索引 (codegraph や graphify) を使うよう rule で案内する。

### 8. ハーネスを変えた前後で数字を比べる

- 見る: improve の「0. 比べる数字」(依頼数、1 依頼あたりのコスト・API 呼び出し・ツール呼び出し、
  ツールの失敗率、キャッシュ読み出し割合)。
- 手順:
  1. 変える直前に、右上の期間を絶対時刻 (例: 変える前の 7 日間) にして数字を控える。
     期間を選んだ状態の URL には `from=` と `to=` が入るので、URL ごと控えておくと後で同じ期間を開き直せる。
  2. rule / skill / spec / モデル選択のうち 1 か所だけ変える。2 か所同時に変えると、どちらの影響か分からない。
  3. 同じ長さの期間が経ったら、ブラウザのタブを 2 つ開き、片方を変える前の期間、もう片方を変えた後の期間にして
     同じパネルを並べる。
  4. 依頼数が 10 件未満のうちは判断しない。依頼の中身で数字が大きく揺れるため。
- 次にすること: 狙った数字が動いていなければ変更を戻すか別の箇所を試す。
  変えた内容と日時は、どちらの結果でもハーネスのリポジトリのコミットに残しておく。

### 9. 新しい属性が届いているか、集計を作る前に何が取れるかを確かめる

- 見る: raw の各節。メトリクスは「メトリクスごとのラベル (キーと値の例)」、ログは
  「イベント種別ごとの件数と属性キー」、トレースは「$span の属性キー」と「全スパン名の属性キー」。
- 分かること: Claude Code の版が上がって増えたメトリクス・イベント・属性。環境変数
  (`OTEL_LOG_USER_PROMPTS` など) を変えたときに、その属性が実際に届き始めたか。
- 次にすること: 使いたい属性の正確な名前をここで確かめてから、usage / traces / improve に
  パネルを足す。ログの属性はドット区切りが `_` に置き換わる (`orca.worktree.name` → `orca_worktree_name`)。
  トレースでは元の名前のまま `span.` か `resource.` を付けて書く。
- 環境変数を足した・外したときは、設定項目別のダッシュボード (`/d/cc-settings`) の該当する 1 枚を開く。
  先頭のタイルがその設定で増える属性の件数で、0 なら届いていない。オフの項目は `/d/cc-setting-off` にまとめてある。

### 10. just share で人に見せるとき

- `just share` は Grafana を trycloudflare.com の URL で公開する。URL とパスワードを知っている人は、
  ダッシュボードのすべてを見られる。特定のパネルだけを見せる仕組みは無い。
- 依頼文、コマンド、読んだファイルのパスがそのまま見える。秘密っぽい値 (トークン、パスワード、鍵) は
  Collector が `<REDACTED>` に伏せてから保存しているが、判定は正規表現によるので、形の決まらない秘密は伏せられない。
  見せる前に raw の `user_prompt` と `tool_result` を開き、見せたくないものが無いかを確かめる。
- 相手に渡すのは閲覧用の `viewer` (Viewer ロール) で、表示されるのもその資格情報。相手はダッシュボードを
  見られるが、編集・保存と Explore はできない。admin のパスワードは `just show grafana-admin` で見る自分用で、渡さない。
- viewer のパスワードは `just share` を打つたびに作り直され、ログイン中のセッションも切れる。前に見せた相手は
  次の共有には入れないので、見せるたびに新しいパスワードを渡す。
- 見せ終わったら Ctrl-C で止める。止めると URL は無効になる。`just show grafana` で
  いま公開中かどうかを確かめられる。

### 11. ワーカーの手戻りを減らす (追加指示・やり直しが多い)

- 見る: Orca orchestration の「1. 要約」の「1 ワーカーあたりの追加指示」、「3. ワーカー別」の
  「ワーカーごとの手戻り」と「追加指示の多いワーカー」。本文は「4. メッセージの流れ」の
  「coordinator ↔ ワーカーのやりとり」。
- 分かること: coordinator がワーカーを出した後に `orca orchestration send` で足した指示 (追加指示) の回数、
  ワーカーからの question、worker_done までの時間、heartbeat が途切れた長さ。追加指示は `ask` への返事を含まない。
  0 が理想で、1 以上は最初の spec に足りない条件があった印。
- 次にすること:
  1. 追加指示の多いワーカーの本文を読み、「最初の spec に書けたはずの条件」(完了条件、触ってよい範囲、
     前提の事実、報告先) かどうかを分ける。書けたものは coordinator の spec の雛形 (core-dispatch / p-mode の手順) に足す。
  2. 途中でユーザーの要望が変わった追加指示は、spec の問題ではない。数えるだけにして雛形は変えない。
  3. 「5. Claude Code との突き合わせ」の「ワーカーごとの手戻りとコスト」で、手戻りの多いワーカーのコストを見る。
     手戻りが多くコストも高いなら、spec を直す効果が大きい。「モデル別の手戻り」で、安いモデルのワーカーだけ
     1 ワーカーあたりの追加指示が多いなら、その種類の仕事はモデルを上げる (場面 6 と合わせて見る)。
  4. worker_done までが長く、heartbeat の最大間隔も長いワーカーは、途中で人の確認待ち (権限、ask) で止まっていた。
     止まった理由が権限なら許可リストに、ask なら spec に判断の基準を書く。
  5. 雛形を直したら、場面 8 の手順で前後の同じ長さの期間を比べる。ワーカーが 10 未満のうちは判断しない。
- 拒否された worker_done や user_takeover が出たら、Orca の運用を疑う: coordinator がワーカーの完了を待たずに
  stop / release / 作り直しをしていないか、完了後に人が端末を引き取る運用になっていないか。

### 12. 話題ごとのトークン・コストを見る (話題チャット方式)

- 見る: Orca orchestration の「6. 話題別・役割別」。「話題ごとのコストとトークン」(話題チャット本体 + その話題の Run の
  ワーカー)、「役割 × モデル別」、「調整コスト比の日次」。
- 前提: worktree 名が `coordinator` なら main-chat、`coordinator-chat-<topic>` なら話題チャット、それ以外はワーカー。
  話題は Run の coordinator の worktree 名 (exporter の `orca_run_coordinator_worktree`) から取る。
  名前の規約を変えたら、集計が外れる ([orca-orchestration.md](orca-orchestration.md) の「話題別・役割別の集計」)。
- 分かること: どの話題にいくら (とどのトークン) かかったか、その内訳が話題チャットとワーカーのどちらか、
  main-chat / topic-chat / worker がどのモデルでどれだけ使ったか。`(不明)` は話題に割れなかった Run
  (ラベルを入れる前に閉じたもの)、`(main-chat 直)` は main-chat が直接回した Run。
- 旧方式 (1 つの coordinator が複数の話題を回す) と比べるとき: 旧方式は話題に割れないので、**期間単位の調整コスト比**
  (調整コスト ÷ ワーカーのコスト) と Dispatch 1 件あたりの調整コストを、切り替え (2026-10-01 04:22 JST) の前後の
  同じ長さの期間で比べる。調整コストは新方式で main-chat + topic-chat、旧方式で `coordinator`
  (worktree 名が空で `vcs_repository_name="coordinator"` のものを含む)。
- 次にすること:
  1. main-chat にコストの大きいモデル (Opus) が入っていたら、main-chat は Sonnet で開く約束が守られていない。
  2. 調整コスト比が切り替え後に下がっていなければ、話題チャットが重い (Opus で回している・長く居座っている)。
     話題別の表で、ワーカーより話題チャット本体が大きい話題を探す。
  3. `(不明)` が大きいときは、exporter が動いていたか (`just orca-exporter status`) と、`terminal list` が通っているかを見る。
- ワーカー分は近似 (`rate` を足したもの) で、短いセッションでは誤差が出る。

## raw ダッシュボードの作り

「Claude Code raw」は、値そのもの (現在値、件数、生のログ行、トレース) は Prometheus / Loki / Tempo の
データソースで引く。属性キーの一覧は PromQL / LogQL / TraceQL では返せないため、Infinity プラグイン
(`yesoreyeram-infinity-datasource`、データソース名 `Backend API`) で各バックエンドの HTTP API を直接叩き、
返ってきた JSON を JSONata で表にしている。

| 表 | 叩く API |
|---|---|
| メトリクスごとのラベル | Prometheus `/api/v1/series` (`claude_code_*` の全系列) |
| イベント種別ごとの件数と属性キー | Loki `/loki/api/v1/query_range` に、全属性名を `label_format` で 1 本の文字列にしたクエリを 5 分刻みで投げて足す |
| スパンの属性キー | Tempo `/api/v2/search/tags` (`q={name="<スパン名>"}`、`scope=span` / `resource`) |

変数「イベント種別」「スパン名」も同じデータソースで引く。Loki の変数 (detected field values) は
最近の数千行しか見ないので、件数の少ないイベント (`user_prompt`、`skill_activated`) が一覧に出ない。
Tempo の `/api/v2/search/tags` は `scope` を付けないと、スパン名で絞ったときに一部のキーしか返さない。
Infinity のクエリの中では `$__range` などの間隔の変数が展開されないので、時間は `${__from:date:seconds}` と
`${__to:date:seconds}` だけで渡している。
