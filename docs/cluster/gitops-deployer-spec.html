gitops-deployer — 仕様書

クライアントの依頼で、home-k8s の deploys/<名前>/ を足す (消す) PR を作り、Argo CD の反映を確かめて終わる。 手順・待機・補償は Temporal の Workflow が持ち、外部 I/O は Activity の Pod が持つ。 実装は services/gitops-deployer/、処理を 1 段ずつ追うのは gitops-deployer-flow.html。Backstage からの呼び出しは後の PR で足す。

1. 経路と認証

APISIX と bff が同じ JWT を 2 回確かめる。APISIX は署名 (realm home-k8s の JWKS)、bff は署名・iss・aud・exp とロール。

種類を選ぶと、要求が流れて止まる所と状態コードが出る。
  • APISIX の経路 /gitops-deployer/api/*: openid-connect (bearer_only・use_jwks、discovery は https://keycloak.taild2b611.ts.net/realms/home-k8s)、limit-count (60 秒に 120 回、超えると 429)、proxy-rewrite (/gitops-deployer を外す) → Service bff:80。
  • bff のロールは client gitops-deployer の client role (resource_access.gitops-deployer.roles): GET は view、POST・DELETE は deploy。POST・DELETE ごとに監査ログ (audit=true・principal・subject・client・action・app・idempotency_key・status)。

2. Workflow の状態遷移と Signal

段は Query status で読める。待つのは Signal argo-event だけで、ポーリングしない。待ちの上限は WAIT_TIMEOUT (20m)。

シナリオを選ぶ。届いた Signal はここに 1 つずつ出る。
  • デプロイが終わる条件: exists・Synced・Healthy・revision がそろい、PRIncluded (PR が merge 済みで、GitHub の compare merge_commit...revision が ahead か identical) が true。削除: exists=false で、PR が merge 済み。
  • 補償 (Compensate): PR が open なら閉じて branch を消す。merge 済みなら gitops-deployer/revert-<番号> で deploys/<名前>/ を merge の前に戻す PR を作り auto-merge。閉じただけの PR なら何もしない。
  • 再試行: git-activity は 2 秒から倍々・最大 1 分・20 回 (NotFound・Invalid は打ち直さない)、store-activity は 1 秒から倍々・最大 30 秒・20 回。

3. GitOps と ApplicationSet

main の deploys/<名前>/ 1 つが Application deploy-<名前> 1 つになる。ApplicationSet gitops-deployer-apps の git directory generator (deploys/*、requeueAfterSeconds 30)。

ボタンで main のディレクトリを足す・消すと、Application が追いかける。

4. Knative Eventing の配線

Application の変化を、Kafka Broker を通して event-receiver に届ける。event-receiver は min-scale 0・max-scale 1 で、イベントが来ると 0→1 に起き、来なくなると 0 に戻る。

流すと、event-receiver が起きて Signal を送る。
  • event-receiver の応答: Signal を送れたら 202。Workflow が無い・走っていない・読めないイベントは 200 で捨てる (Broker は打ち直さない)。2xx は本文を付けない (Kafka Broker の dispatcher は CloudEvent でない本文の付いた応答を失敗として Dead Letter へ送る)。Temporal に届かなければ 503。
  • dead-letter は Trigger を持たない Kafka Broker で、イベントはトピック knative-broker-gitops-deployer-dead-letter に残る。

5. Dapr と Redis・Kafka

アプリは Dapr の API (サイドカー 127.0.0.1:3500) だけを使い、Redis と Kafka のクライアントを持たない。Dapr を持つのは bff・api・store-activity。
